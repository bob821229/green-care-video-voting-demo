# 投票與防護機制說明

本文件整理正式 Node.js／Express 版本實際採用的觀看紀錄、投票、防機器人、限流與資料維護規則，也說明 GitHub Pages 展示版如何模擬相同的使用流程。展示版用於與需求方確認畫面及規則；正式上線仍必須使用後端、SQLite 與安全防護。

## 1. 整體流程

1. 使用者第一次呼叫 API 時，後端產生匿名裝置 ID，簽章後存入 `vote_device` Cookie。
2. 使用者開啟作品，前端向 `/api/watch/start` 建立或沿用觀看 Session。
3. 影片播放期間，前端約每 5 秒向 `/api/watch/progress` 回報一次；暫停、緩衝、播放結束、關閉彈窗或切換作品前會再補送一次。
4. 後端只累加合理、可驗證的前景播放時間；有效觀看達影片長度 80% 後，該作品才取得投票資格。
5. 使用者投票前必須通過 Google reCAPTCHA；投票資格、票數上限及重複投票均由後端再次檢查。票滿時須先前往原作品取消，再回新作品投票。
6. 排行頁每 30 秒抓取一次結果；後端會共用 5 秒結果快取，降低 SQLite 查詢量。

## 2. 裝置辨識

- 系統不要求登入，以帶有伺服器簽章的 `vote_device` Cookie 辨識瀏覽器裝置。
- Cookie 設定為 `HttpOnly`、`SameSite=Lax`，正式環境會加上 `Secure`，有效期一年。
- 簽章使用 `APP_SECRET`，正式環境不可使用預設開發密鑰。
- 裝置的 `last_seen_at` 最多每 5 分鐘更新一次，避免每個觀看進度請求都寫入 SQLite。

限制：這只能限制同一瀏覽器；清除 Cookie、使用無痕模式、換瀏覽器或換裝置仍可能被視為新裝置。因此仍需搭配 reCAPTCHA、IP 風險判斷、流量限制與人工稽核。

## 3. 觀看進度規則

### 建立觀看 Session

- API：`POST /api/watch/start`
- 影片必須存在於 `videos.json`。
- 影片長度必須介於 10 至 7,200 秒。
- 同一裝置在 30 分鐘內重新開啟相同作品，且影片長度差小於 2 秒時，會沿用最近的 Session，不會持續新增資料列。

### 回報進度

- API：`POST /api/watch/progress`
- 前端正常播放時約每 5 秒回報；暫停、緩衝、播放結束、關閉彈窗及切換上一部／下一部前會補送一次，減少最後數秒未被採計的情況。
- 一般回報在 3 秒內重複送出時，只回傳既有狀態，不寫入新的觀看進度。上述播放狀態轉換的補送可略過這項 3 秒節流，但仍須通過所有播放合理性檢查。
- Session 必須具有有效簽章，且必須屬於目前裝置。
- 只有同時符合以下條件才會累加有效觀看秒數：
  - YouTube Player 回報正在播放。
  - 網頁位於前景，`document.visibilityState` 為 `visible`。
  - 播放速度大於 0 且不超過 1.25 倍。
  - 播放位置沒有倒退或不合理跳躍。
  - 播放位置增量與實際經過時間相符。
- 單次可累加的實際經過時間最多採計 10 秒。
- 若影片播完後重新從開頭播放，系統會保留已累積的有效觀看秒數，只重設本次播放位置基準，避免位置倒退造成後續正常播放都無法採計。
- 累計有效觀看達影片長度 80% 時寫入 `qualified_at`，之後才可對該作品投票。
- 快轉、背景播放、異常跳轉及偽造的不合理進度不列入有效觀看時間。

## 4. 投票規則

- 活動時間由 `ACTIVITY_START` 與 `ACTIVITY_END` 控制，只有 `active` 狀態可以新增或取消。
- 個人組與團體組各可持有 2 張有效票。
- 同一裝置不能同時對同一作品持有兩張有效票。
- 投票前必須已對該作品完成 80% 有效觀看。
- 新增投票必須通過 Google reCAPTCHA 後端驗證。
- 不提供直接改投；票滿時必須先開啟原作品、確認並取消原票，再回新作品重新投票。
- 取消投票不要求再次完成 reCAPTCHA，但仍受活動期間及限流規則約束。
- 取消不會刪除原始票，而是將狀態改為 `cancelled`，保留稽核紀錄。

票券可能狀態：

- `valid`：有效票，會計入公開排行。
- `flagged`：風險票，暫不計入公開排行，供後台檢查。
- `cancelled`：使用者取消的原票。
- `void`：管理員填寫原因後作廢的票。

## 5. 防機器人與風險評分

### reCAPTCHA

- 正式環境必須設定 `RECAPTCHA_SITE_KEY`、`RECAPTCHA_SECRET_KEY` 與 `RECAPTCHA_EXPECTED_HOSTNAME`。
- Token 由前端取得，但驗證由後端直接向 Google 執行，逾時上限為 8 秒。
- reCAPTCHA 保護投票；觀看進度另由簽章 Session、合理性檢查與限流保護。

### 匿名風險訊號

- 原始 IP 不寫入投票資料表，只儲存以 `APP_SECRET` 產生的 HMAC 雜湊。
- 前端裝置訊號包含平台、語言、螢幕尺寸及時區，後端同樣只保存雜湊。
- 系統會參考同一 IP 最近 10 分鐘的投票數，以及相同裝置訊號是否出現在其他裝置 ID。
- 風險分數達 60 分的票標記為 `flagged`，並寫入 `risk_events`，不直接計入排行。
- 這是輔助風險判斷，不等同真人身分驗證，也不能單獨保證「一人一票」。

## 6. API 限流

目前限流資料保存在 Node.js 執行個體的記憶體中，以 60 秒滑動窗口計算：

| API／動作 | 限制 |
| --- | --- |
| 建立觀看 Session | 每個 IP 120 次／分鐘 |
| 建立觀看 Session | 每個裝置 12 次／分鐘 |
| 回報觀看進度 | 每個 IP 600 次／分鐘 |
| 回報觀看進度 | 每個裝置 60 次／分鐘 |
| 回報觀看進度 | 每個 Session 20 次／分鐘 |
| 投票、取消合計 | 每個裝置 10 次／分鐘 |
| 投票、取消合計 | 每個 IP 30 次／分鐘 |

超過限制時，API 回傳 HTTP `429 Too Many Requests`，並附上 `Retry-After: 60`。

重要限制：記憶體限流會在 Node.js 重啟後歸零，而且多台 Node.js 之間不會共用。若未來水平擴充，應改用 Redis 等集中式限流；正式公開活動也應在 Cloudflare 或 IIS 前層再做 IP／路徑限流。

## 7. 排行與快取

- 公開結果只統計 `status = 'valid'` 的票。
- 同票數時依作品 ID 由小到大排序。
- 前端結果頁及首頁摘要每 30 秒更新一次。
- 後端 `/api/results` 使用 5 秒記憶體快取，讓同一時間的大量訪客共用查詢結果。
- 新增投票、取消或管理員作廢成功後，會立即清除快取，因此下一次查詢可取得新結果。
- API 回傳 `Cache-Control: private, max-age=5`，瀏覽器可短暫重用，但共享代理不會直接快取使用者端回應。

## 8. SQLite 與資料維護

- 資料庫預設位置：`data/votes.db`，也可透過 `DB_PATH` 指定。
- SQLite 啟用 WAL 模式與 Foreign Key。
- 主要資料表：`devices`、`watch_sessions`、`votes`、`risk_events`、`audit_logs`。
- 伺服器每 15 分鐘執行一次維護：刪除超過 24 小時、尚未達標且沒有被任何票引用的觀看 Session。
- 已達標的 Session，以及被投票引用的 Session 不會被上述清理移除。
- 應定期備份 `data/votes.db`，且只允許執行 Node.js 的 IIS 應用程式帳號存取資料夾。

SQLite 適合單台主機、中小型活動及以讀取為主的流量。若出現大量同時寫入、需要多台應用伺服器，或活動風險與可用性要求提高，建議遷移至 SQL Server／PostgreSQL，並使用 Redis 或前置服務進行集中式限流。

## 9. Windows IIS 正式上線檢查

- 使用 HTTPS。
- 設定至少 32 字元且不可預測的 `APP_SECRET`，以及獨立的 `ADMIN_KEY`。
- 設定正式 reCAPTCHA 金鑰及正確網域。
- IIS 作為反向代理時設定 `TRUST_PROXY=1`，並確認只有可信任代理能連到 Node.js，否則 IP 判斷可能不正確。
- 使用 IIS URL Rewrite／ARR 將請求轉送至常駐的 Node.js 服務；用服務管理工具確保 Node.js 異常後可自動重啟。
- 在 IIS、Cloudflare 或防火牆限制 `/api/watch/start`、`/api/watch/progress` 與 `/api/votes` 的異常流量。
- 限制 request body 大小；應用程式目前的 JSON 上限為 20 KB。
- 監控 HTTP 429、HTTP 5xx、CPU、記憶體、磁碟空間、資料庫大小及 API 延遲。
- 活動前先做備份還原演練與壓力測試；不要只用瀏覽器手動測試判斷負載能力。

## 10. GitHub Pages 展示版與正式版的一致性

GitHub Pages 沒有 Node.js 與資料庫，因此 `public/api-client.js` 會在瀏覽器內用 Mock API 模擬後端。為了讓需求確認結果能延續到正式版，目前兩種版本採用相同的核心規則：

- 個人組與團體組各 2 票、不可重複投同一作品；票滿時須先取消原票，再投新作品。
- 有效觀看達 80% 才可投票。
- 正常播放每 5 秒回報，播放狀態改變、關閉或切換作品前補送一次。
- 一般回報採 3 秒節流；播放速度、前景狀態、播放位置增量及實際經過時間都要合理才累計。
- 30 分鐘內重新開啟同作品且片長相近時，沿用同一觀看 Session。
- 影片重新從開頭播放時保留累積秒數並重設位置基準。
- 排行、作品狀態、投票確認及取消的使用流程維持一致；直接改投已依 2026-09-18 使用者決定停用。

受純靜態網站限制，下列項目無法與正式版完全相同：

- 展示版的觀看 Session 只存在目前分頁記憶體，重新整理後 Session 會消失；已累積的觀看比例與票券則保存在該瀏覽器的 `localStorage`。
- 展示版沒有 SQLite、簽章 Cookie、真實 reCAPTCHA、IP／裝置／Session 限流、風險評分、稽核紀錄及後台作廢功能。
- 展示版排行由固定的示範票數加上本機投票組成，不是多人共用的即時結果。
- 使用者可清除 `localStorage` 重設展示資料，因此展示版不能用於正式活動或防弊驗證。

結論：GitHub Pages 適合確認畫面、文案、觀看門檻與投票流程；資安、多人資料一致性、負載及防灌票能力必須以正式後端環境驗收。

## 11. 測試與相關檔案

執行測試：

```bash
npm test
```

目前測試涵蓋票數上限、同作品重複票、票滿導向原作品、取消後重投、管理員作廢、結果快取失效、觀看 Session 沿用、觀看限流、過密回報節流、播放狀態轉換補送及重新播放位置重設。

相關實作位置：

- `server.js`：API、限流、觀看判斷、快取及定期清理。
- `db.js`：SQLite Schema、索引與 WAL 設定。
- `public/app.js`：YouTube 播放器、每 5 秒進度回報與播放狀態轉換補送。
- `public/api-client.js`：GitHub Pages Mock API，模擬正式版的核心觀看與投票規則。
- `test/api.test.js`：API 整合測試。
- `.env.example`：正式環境變數範例。
