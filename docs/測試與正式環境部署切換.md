# GreenCare 測試站與正式站部署切換手冊

本文件記錄將 GreenCare 部署至遠端 Windows Server 2016／IIS 10 時，測試站與正式站之間需要分開建立、設定及驗收的項目。

## 1. 環境對照

| 項目 | 測試站 | 正式站 |
|---|---|---|
| 網址 | `ecoia-demo.triwra.org.tw` | `greencare.triwra.org.tw` |
| 建議 App Pool | `ecoia-demo.triwra.org.tw` | `greencare.triwra.org.tw` |
| Data Protection 目錄 | `D:\Webs_SSL\greencare_shared\test-keys` | `D:\Webs_SSL\greencare_shared\production-keys` |
| `Security__AppSecret` | 測試站專用 | 正式站專用，禁止沿用測試值 |
| `Captcha__ExpectedHostname` | `ecoia-demo.triwra.org.tw` | `greencare.triwra.org.tw` |
| SQL Server | 測試資料庫及測試帳號 | 正式資料庫及正式最小權限帳號 |

> 表中的 App Pool 名稱是建議值。執行 ACL 指令前，必須先在 IIS 管理員確認站台實際使用的「應用程式集區」名稱，不能只依網站名稱推測。

## 2. 共通安全原則

- 測試站與正式站使用不同的 `Security__AppSecret`。
- 測試站與正式站使用不同的 Data Protection 目錄。
- 不要將本機 `.local/data-protection-keys` 的 XML 複製到伺服器。
- 不要將測試站的 XML 金鑰複製到正式站。
- Data Protection 目錄必須位於網站發布目錄之外，重新部署時不得刪除或覆蓋。
- `AppSecret`、SQL 密碼與 CAPTCHA Secret 不得提交至 GitHub、寫入文件或傳送到對話中。
- Data Protection XML 只有在應用程式功能首次實際要求建立／使用 Data Protection key 時才會產生；產生後應納入受控的伺服器備份。

## 3. 部署測試站

### 3.1 確認實際 App Pool

在 IIS 管理員中：

1. 開啟「站台」。
2. 選取測試站。
3. 右側選擇「基本設定」。
4. 記下「應用程式集區」的實際名稱。

以下範例假設名稱為 `ecoia-demo.triwra.org.tw`。

### 3.2 產生測試站 AppSecret

在遠端伺服器的 PowerShell 執行：

```powershell
$bytes = New-Object byte[] 48
$rng = [System.Security.Cryptography.RandomNumberGenerator]::Create()
$rng.GetBytes($bytes)
$rng.Dispose()

$testAppSecret = [Convert]::ToBase64String($bytes)
$testAppSecret
$testAppSecret.Length
```

長度應為 `64`。將輸出的完整字串放入測試站 `web.config`，不要將真實值寫入本文件。

### 3.3 建立測試站 Data Protection 目錄

使用系統管理員 PowerShell：

```powershell
New-Item `
  -ItemType Directory `
  -Path 'D:\Webs_SSL\greencare_shared\test-keys' `
  -Force

icacls 'D:\Webs_SSL\greencare_shared\test-keys' `
  /grant 'IIS AppPool\ecoia-demo.triwra.org.tw:(OI)(CI)M'
```

若實際 App Pool 名稱不同，必須替換指令中的名稱。

確認目錄及 ACL：

```powershell
Test-Path 'D:\Webs_SSL\greencare_shared\test-keys'
icacls 'D:\Webs_SSL\greencare_shared\test-keys'
```

### 3.4 測試站 web.config 設定

以下內容必須位於 `<aspNetCore>...</aspNetCore>` 內的 `<environmentVariables>`：

```xml
<environmentVariable name="ASPNETCORE_ENVIRONMENT"
                     value="Production" />

<environmentVariable name="Security__AppSecret"
                     value="測試站專用的64字元隨機值" />

<environmentVariable name="Security__DataProtectionKeysPath"
                     value="D:\Webs_SSL\greencare_shared\test-keys" />

<environmentVariable name="Captcha__SiteKey"
                     value="測試站使用的Site Key" />

<environmentVariable name="Captcha__SecretKey"
                     value="測試站使用的Secret Key" />

<environmentVariable name="Captcha__ExpectedHostname"
                     value="ecoia-demo.triwra.org.tw" />

<environmentVariable name="ConnectionStrings__GreenCare"
                     value="測試資料庫連線字串" />

<!-- 僅供測試站驗收使用；正式站禁止使用，正式部署前必須移除 -->
<environmentVariable name="Activity__StartsAt"
                     value="2026-01-01T00:00:00+08:00" />

<environmentVariable name="Activity__EndsAt"
                     value="2026-12-31T23:59:59+08:00" />
<!-- 測試活動期間設定結束 -->
```

reCAPTCHA 金鑰必須允許 `ecoia-demo.triwra.org.tw`。`ExpectedHostname` 只填 hostname，不包含 `https://`、路徑、斜線或連接埠。

`Activity__StartsAt` 與 `Activity__EndsAt` 是為了讓測試站在正式活動開始前也能驗收觀看、投票及取消流程。這兩項只允許存在於測試站 `web.config`；不得寫入共用發布成品，也不得複製到正式站。

### 3.5 啟動及驗證測試站

1. 儲存 `web.config`。
2. 回收測試站 App Pool。
3. 開啟測試站網址。
4. 開啟 `/api/health`，確認 `activity.state` 為 `active`，且起訖時間是上述測試期間。
5. 確認程式使用的是預期目錄；若已有功能實際使用 Data Protection，下列指令會看到自動產生的 `key-....xml`：

```powershell
Get-ChildItem 'D:\Webs_SSL\greencare_shared\test-keys'
```

6. 執行本文第 5 節的驗收清單，包含觀看達 80%、投票及取消。

> 不需要手動建立 XML。僅註冊 Data Protection 並不保證啟動時立即建立金鑰；必須等程式功能首次實際使用 Data Protection。現階段目錄為空不代表設定失敗，應以目錄存在、ACL 正確及網站能正常啟動作為部署驗證。

## 4. 從測試站移轉至正式站

正式站不是直接複製測試站的安全設定。發布成品可以使用同一份已驗證 artifact，但環境設定、秘密與持久化金鑰必須重新建立。

### 4.1 部署前確認

- [ ] 測試站功能與 IIS smoke test 已通過。
- [ ] 正式 SQL Schema 已由 DBA 人工套用並核對 `SchemaVersions`。
- [ ] 正式 SQL 應用程式帳號已建立，且僅有必要權限。
- [ ] 正式 DNS 與 HTTPS 憑證已完成。
- [ ] reCAPTCHA 金鑰已允許 `greencare.triwra.org.tw`。
- [ ] 已記錄 artifact 版本與 SHA-256。
- [ ] 已確認正式 App Pool 實際名稱。

正式資料庫必須命名為 `GreenCare_Production`，不得清空後沿用 `GreenCare_Development`。依序套用 `001_initial_schema.sql`、`002_application_permissions.sql`、`003_video_catalog.sql`，再使用正式作品置換範本。建立正式 SQL 使用者並加入 `GreenCareAppRole` 後，移除其 `db_owner` 身分。

正式上線門檻檢查（將 `GreenCare_Production_User` 替換成實際正式資料庫使用者）：

```powershell
sqlcmd -S 'labdb' -E -d 'GreenCare_Production' -b -f 65001 `
  -v ExpectedDatabase='GreenCare_Production' `
     AppUserName='GreenCare_Production_User' `
     RequireEmptyActivity='1' `
     RequireOfficialCatalog='1' `
  -i 'database\verify\006_verify_environment_readiness.sql'
```

必須看到 `Environment readiness verification passed.` 才能讓正式 IIS 連線。若仍有 Demo 影片、測試票、缺少 Schema 或正式帳號仍為 `db_owner`，腳本會直接失敗。

### 4.2 產生正式站 AppSecret

在遠端伺服器重新執行下列指令，產生一組與測試站不同的值：

```powershell
$bytes = New-Object byte[] 48
$rng = [System.Security.Cryptography.RandomNumberGenerator]::Create()
$rng.GetBytes($bytes)
$rng.Dispose()

$productionAppSecret = [Convert]::ToBase64String($bytes)
$productionAppSecret
$productionAppSecret.Length
```

長度應為 `64`。此值必須固定保存，不得在每次部署時重新產生。

### 4.3 建立正式站 Data Protection 目錄

以下範例假設正式 App Pool 名稱為 `greencare.triwra.org.tw`：

```powershell
New-Item `
  -ItemType Directory `
  -Path 'D:\Webs_SSL\greencare_shared\production-keys' `
  -Force

icacls 'D:\Webs_SSL\greencare_shared\production-keys' `
  /grant 'IIS AppPool\greencare.triwra.org.tw:(OI)(CI)M'
```

確認：

```powershell
Test-Path 'D:\Webs_SSL\greencare_shared\production-keys'
icacls 'D:\Webs_SSL\greencare_shared\production-keys'
```

### 4.4 正式站 web.config 設定

```xml
<environmentVariable name="ASPNETCORE_ENVIRONMENT"
                     value="Production" />

<environmentVariable name="Security__AppSecret"
                     value="正式站專用的64字元隨機值" />

<environmentVariable name="Security__DataProtectionKeysPath"
                     value="D:\Webs_SSL\greencare_shared\production-keys" />

<environmentVariable name="Captcha__SiteKey"
                     value="正式站使用的Site Key" />

<environmentVariable name="Captcha__SecretKey"
                     value="正式站使用的Secret Key" />

<environmentVariable name="Captcha__ExpectedHostname"
                     value="greencare.triwra.org.tw" />

<environmentVariable name="ConnectionStrings__GreenCare"
                     value="正式資料庫連線字串" />
```

正式站還必須確認 Production 活動期間為台北時間：

- 開始：`2026-10-12 10:00`
- 結束：`2026-10-23 17:00`

正式站 `web.config` 不得包含測試用的 `Activity__StartsAt`／`Activity__EndsAt` 覆寫。若由測試站設定複製而來，必須先移除這兩個節點，讓程式使用 `appsettings.Production.json` 的正式活動期間；啟動後再以 `/api/health` 核對。

### 4.5 啟動及確認正式金鑰

1. 儲存正式站 `web.config`。
2. 啟動或回收正式 App Pool。
3. 開啟正式站網址。
4. 檢查正式目錄；若已有功能實際使用 Data Protection，目錄會產生自己的 XML：

```powershell
Get-ChildItem 'D:\Webs_SSL\greencare_shared\production-keys'
```

5. 確認測試與正式站使用不同目錄；日後產生的檔案必須彼此獨立。
6. 執行本文第 5 節的驗收清單。

## 5. 每個環境的部署後驗收

- [ ] 網站以 HTTPS 正常開啟，憑證與重新導向正確。
- [ ] `/`、`/results` 及重新整理正常。
- [ ] `/api/health` 回傳成功。
- [ ] 活動期間符合目前環境：測試站為核准的測試期間；正式站為 `2026-10-12 10:00` 至 `2026-10-23 17:00`（台北時間）。
- [ ] `/api/bootstrap` 回傳作品及正確活動期間。
- [ ] SQL Server 連線正常，沒有帳號或權限錯誤。
- [ ] reCAPTCHA 可顯示並成功完成後端驗證。
- [ ] `Captcha__ExpectedHostname` 與目前網址一致。
- [ ] 可以建立觀看 Session，且背景播放不增加有效觀看進度。
- [ ] 達到 80% 後可以投票。
- [ ] 每組最多兩票、取消後再投及票數結果均正常。
- [ ] 回收 App Pool 後網站仍可啟動，既有 Cookie 行為正常。
- [ ] Data Protection 目錄存在且 App Pool 具有必要的讀寫權限；若程式已實際使用 Data Protection，確認 XML 可正常產生。
- [ ] Windows Event Viewer 沒有持續的 500.30 或 OptionsValidationException。
- [ ] IIS／應用程式 log 沒有洩漏 SQL 密碼、AppSecret、CAPTCHA Secret 或 Cookie。

## 6. 後續重新部署注意事項

- 可以替換網站發布目錄中的應用程式檔案，但不要刪除 `test-keys` 或 `production-keys`。
- 同一環境後續部署沿用原本的 `Security__AppSecret`，不要重新產生。
- `web.config` 若隨 artifact 被覆蓋，部署前必須重新套用該環境的受控設定。
- 變更網域時，同步調整 reCAPTCHA 允許網域及 `Captcha__ExpectedHostname`。
- 若確實輪替 AppSecret，既有裝置 Cookie、簽署 Token 及歷史雜湊比對可能失效，必須先評估影響。
- 若遺失 Data Protection XML，既有受保護資料可能無法解讀；應從受控備份復原，不要任意重建。

## 7. 故障排查

### HTTP 500.30／Security 設定驗證失敗

檢查：

- `Security__AppSecret` 是否至少 32 字元，建議使用本文件產生的 64 字元值。
- 設定名稱中是否使用兩個半形底線 `__`。
- `<environmentVariables>` 是否位於 `<aspNetCore>...</aspNetCore>` 內。
- 修改的是否為 IIS 目前實際站台目錄內的 `web.config`。
- 儲存後是否已回收正確的 App Pool。

### Data Protection 目錄沒有 XML

目前程式已設定持久化位置與 Windows DPAPI，但如果尚無功能實際呼叫 Data Protection，空目錄是正常情況。不要自行建立或從本機複製 XML。若未來功能已實際使用 Data Protection 仍無法產生，再檢查：

檢查：

- 目錄是否存在。
- `Security__DataProtectionKeysPath` 是否與實際路徑完全一致。
- `icacls` 授權的是否為正確 App Pool identity。
- App Pool 是否取得目錄的 `(OI)(CI)M` 權限。
- 不要將 Markdown 顯示用的跳脫字元誤寫進實際路徑；實際根目錄應為 `D:\Webs_SSL`，不是 `D:\Webs\_SSL`。

### CAPTCHA 啟動或驗證失敗

檢查：

- `SiteKey` 是 Google Cloud reCAPTCHA 金鑰頁面的 ID。
- `SecretKey` 是「舊版 reCAPTCHA 密鑰」，不得公開。
- 金鑰類型為 Website／Checkbox challenge。
- Google Cloud 允許的網域包含目前站台 hostname。
- `ExpectedHostname` 不包含協定、路徑或連接埠。
