# GreenCare 技術棧遷移計畫書

## 1. 文件目的

將現有「原生 JavaScript + Node.js/Express + SQLite」投票網站改寫為：

- 前端：Vue 3 + Vite
- 後端：ASP.NET Core Web API（.NET 8）
- 資料存取：Entity Framework Core 8
- 資料庫：Microsoft SQL Server
- 正式環境：Windows Server 2016 x64 + IIS 10

本次以技術棧遷移為主，首頁、結果頁、圖片、響應式版面、YouTube 播放及觀看進度維持目前行為；投票異動依 2026-09-18 使用者確認調整為「先取消原票，再投新作品」，不提供直接改投。

> 版本提醒：.NET 8 將於 2026-11-10 結束官方支援。本案仍依指定使用 .NET 8，但正式上線後須立即安排升級至 .NET 10 LTS。

## 2. 已定案範圍

### 2.1 納入

- Vue 重建首頁及結果頁，外觀與目前版本一致。
- .NET 8 重建公開 API、Cookie、觀看資格、投票規則、風險判定、限流、快取及稽核紀錄。
- SQL Server 建立全新資料庫，不匯入目前 SQLite 資料。
- 保留 GitHub Pages 展示版，改由 Vue Demo mode 與 Mock API 提供。
- ASP.NET Core 同一站台提供 Vue 靜態檔案及 `/api`，避免 CORS 與跨站 Cookie 問題。
- 新版先在新目錄平行建置；完成測試與驗收後才移除 Node.js/SQLite 舊碼。

### 2.2 不納入

- 不重新設計 UI、活動規則或 YouTube 播放流程。
- 不搬移 `votes.db`、`verification.db` 或其他既有測試資料。
- 不移植目前未公開使用的 `admin.html`、管理摘要 API 與作廢票 API。
- 不採用 EF Core Code First migrations，也不允許應用程式啟動時自動修改正式資料庫 Schema。

## 3. 目標架構

建議專案配置：

```text
src/
  greencare-web/              Vue 3 + Vite
  GreenCare.Api/              ASP.NET Core Web API
tests/
  GreenCare.Api.Tests/        單元與 API 整合測試
database/
  scripts/                    依版本排序的 SQL 異動腳本
  rollback/                   必要的回復腳本
docs/
```

開發環境由 Vite dev server 提供前端，並將 `/api` proxy 至 ASP.NET Core。正式發布時先執行 Vite build，再將輸出納入 ASP.NET Core 的靜態檔案發布目錄，由 IIS 上的一個 ASP.NET Core 站台統一提供。

正式主機不需要安裝 Node.js；Node.js 只在開發機或 CI 建置 Vue 時使用。

## 4. 前端遷移

- 使用 Vue 3 Composition API、Vue Router 與 Vite。
- 路由至少包含首頁 `/` 與結果頁 `/results`；舊的 `/results.html` 可保留相容導向。
- 沿用目前 CSS、圖片、作品卡、分類頁籤、觀看 Dialog、確認 Dialog、票數摘要與行動版斷點。
- 包裝 YouTube IFrame Player API，維持開始觀看、進度回報、切換作品及背景播放判斷。
- 建立單一 API client：正式模式呼叫同源 `/api`；Demo mode 使用 mock 資料及 `localStorage`。
- Demo mode 不得傳送資料至正式 API 或 SQL Server。
- `videos.json` 繼續作為 30 支作品的版本控管設定來源。

## 5. 後端遷移

ASP.NET Core API 須保留以下公開端點與主要 JSON 行為：

| Method | Path | 用途 |
|---|---|---|
| GET | `/api/bootstrap` | 作品、裝置票數、觀看進度、活動狀態及前端設定 |
| POST | `/api/watch/start` | 建立或重用觀看 Session |
| POST | `/api/watch/progress` | 回報並驗證有效觀看進度 |
| POST | `/api/votes` | 新增投票 |
| DELETE | `/api/votes/{id}` | 取消投票並保留紀錄 |
| GET | `/api/results` | 取得各組即時排行 |

後端行為要求：

- 使用 HttpOnly、SameSite=Lax Cookie 識別裝置；正式 HTTPS 環境啟用 Secure。
- 使用 ASP.NET Core Data Protection 保護 Cookie，金鑰須放在站台目錄以外的持久化位置。
- IP 與裝置訊號以伺服器密鑰進行 HMAC 雜湊，不保存原始 IP。
- 保留每組最多 2 票、同作品不得重複、觀看達 80% 才能投票等規則。
- 背景播放、暫停、異常倍速、快轉跳過及不合理位置變化不得累積有效進度。
- 票滿時必須先前往原作品確認並取消一票，再到新作品重新完成 CAPTCHA 與投票；不提供直接改投 API。
- 投票截止後禁止新增或取消。
- 結果只統計 `valid` 票，維持 5 秒伺服器快取及前端每 30 秒更新。
- 使用 ASP.NET Core rate limiting 或等價服務維持現有裝置、IP、Session 限流規則。
- 統一處理例外、回傳正確 HTTP 狀態碼，並避免將例外或連線資訊回傳前端。

## 6. SQL Server 與資料庫異動原則

EF Core 僅負責 entity mapping、查詢、交易與資料存取，不使用 `dotnet ef migrations` 管理 Schema。

資料庫異動流程：

1. 開發者依核准的資料模型撰寫版本化 SQL，例如 `database/scripts/001_initial_schema.sql`。
2. SQL 腳本須包含 table、foreign key、check constraint、index、default value，以及可重複執行或明確的前置條件檢查。
3. 每份 SQL 先在空白開發資料庫執行，再針對既有 Schema 測試升級路徑。
4. 由 DBA 或部署人員人工審核 SQL、備份資料庫並於維護時段手動執行。
5. 執行後核對 Schema、constraint、index 與腳本版本紀錄。
6. 正式站台使用者只取得資料讀寫權限，不取得 `ALTER`、`CREATE` 或 `DROP` 權限。
7. 破壞性異動必須另附回復腳本或明確的資料回復方式。

預計資料表：

- `Devices`
- `WatchSessions`
- `Votes`
- `RiskEvents`
- `AuditLogs`
- `SchemaVersions`：紀錄人工執行過的 SQL 腳本版本、時間與執行人。

日期時間以 UTC `datetime2` 儲存；活動設定可使用含 `+08:00` offset 的設定值，進入系統後轉為 UTC 比較。

## 7. 設定與安全

- 非敏感預設值放在 `appsettings.json`；正式連線字串、HMAC 密鑰及 CAPTCHA 密鑰以 IIS 環境變數提供。
- 活動期間依環境分離：Development／本機測試預設全年開放；Production 固定為 2026-10-12 10:00 至 2026-10-23 17:00（Asia/Taipei），部署時必須驗證未誤用開發設定。
- 正式環境必須使用 HTTPS、至少 32 字元的應用程式密鑰及最小權限 SQL 帳號。
- 啟用 forwarded headers，且只信任實際 IIS/proxy，以取得正確來源 IP。
- 限制 request body 大小並驗證所有 DTO。
- Data Protection 金鑰目錄僅允許 IIS App Pool identity 讀寫。
- 應用程式記錄結構化日誌，但不得記錄原始 IP、Cookie、CAPTCHA token、密鑰或完整連線字串。

## 8. 測試與驗收標準

- API 測試涵蓋裝置 Cookie、觀看資格、每組票數上限、重複票、取消後重投、活動期限、限流、風險票及結果排序。
- SQL 整合測試必須使用真實 SQL Server；不得以 EF InMemory 取代 constraint、index 或 transaction 測試。
- Vue 測試涵蓋頁面載入、分類切換、影片 Dialog、投票、票滿後前往原作品取消、錯誤訊息及結果更新。
- 對現有版本執行桌面、平板及手機畫面比對，非預期的布局、字型、顏色、間距及互動差異皆視為未通過。
- GitHub Pages Demo build 可獨立運作，且不會呼叫正式 API。
- IIS smoke test 通過首頁、SPA 路由、API、Cookie、YouTube、CAPTCHA、SQL 連線與活動時間測試。

## 9. 切換策略

1. 在新目錄完成 Vue、.NET 及 SQL Server 版本。
2. 以舊版作為 UI、API 與操作行為比對基準。
3. 通過本機 checklist、CI、測試環境 IIS 驗收及 SQL 腳本演練。
4. 產出可回復的 IIS 發布包及資料庫備份。
5. 正式切換後執行 smoke test。
6. 穩定觀察完成後，再移除 Express、SQLite 與舊前端程式。

## 10. 風險

- .NET 8 即將停止支援：建立 .NET 10 升級工作項目，最遲於 2026-11-10 前完成。
- UI 等價容易產生細節偏差：使用基準截圖與實機 checklist 驗收。
- SQLite 與 SQL Server SQL 語意不同：所有限制、交易及日期查詢以 SQL Server 整合測試確認。
- 人工執行 SQL 可能漏版：以 `SchemaVersions`、部署核對表及執行紀錄控管。
- IIS 回收可能使記憶體限流／快取重置：接受與現有單機行為等價；若未來多站台或多節點，再導入集中式服務。
